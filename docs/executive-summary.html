Why the literal uniqueness rule stops us

We independently read the SHA-pinned owner-mirror footprint and the registered r13-lattice-s5 raster. Of 5,167,373 footprint pixels, only 6,649 are more than three pixels away from a lattice dot. For any set of 37,654 distinct dots, at least 37,654 − 6,649 = 31,005 must be within the lattice neighborhood: 82.34%. The requested stop is strictly greater than 70%.

The counting bound first forces a stop at 22,164 dots. It does not prove every smaller candidate is unique, or that lattice proximity represents geological similarity. The literal protocol allows no density exception. Moving dots into uncovered holes solely to evade a guard would not establish geological merit.

About the range error

The official problem description specifies one float32 layer, probabilities in [0,1], the same CRS, resolution and bounds as the training data, and null or NaN outside the bounds. The submission form additionally requires the same shape and geotransform as the example.

We do not have the rejected file or organizer diagnosis. An all-finite zero-outside raster may satisfy a whole-array range check but does not mask the owner-mirror’s outside footprint. A NaN-outside raster may satisfy the null convention but fail an indiscriminate whole-array range check. The public wording refers to bounds; whether the platform treats the irregular mirror footprint as “outside” is not established. We do not claim either encoding guarantees acceptance.

The local inspector reports both conditions separately, detects NaN, infinity, masks and out-of-range values, and compares the reopened file with a supplied sample. Its conservative combined policy is stricter than the confirmed portal behavior; it does not authorize an upload. An internal mask with finite underlying pixels can pass both local checks in synthetic tests, but portal acceptance remains unverified. See the exact KPL-36 format inspection ↗

How to submit, once a file is approved

  1. Wait for a new candidate to pass the scientific gates. It needs an assigned lane, feature-alone leakage canaries, a buffered whole-segment visible-only holdout, a paired confidence interval beating the same-evaluator incumbent, and surface plus final-dot checks against the complete current registry.
  2. Run the saved-byte format inspection. Compare the exact TIFF against the authenticated organizer example. Check one float32 band, CRS, shape, affine transform, in-footprint finite [0,1] values, and the outside encoding. Record the TIFF’s SHA-256 and the machine receipt. Local checks do not establish organizer acceptance.
  3. Run the separate slot selector. The research protocol forbids a scientific run from selecting a real slot. Check the availability shown on your competition submission page. The rules mention three per week, but DrivenData staff clarified that the website limit prevails. We cannot see this account’s remaining allowance.
  4. Upload the exact approved file. Enroll/sign in to DrivenData, open the competition’s Submit page, choose “Make new submission,” select the approved single-band TIFF (or a ZIP containing one TIFF), and enter its short identifying note. No valid filename or note can be supplied yet for this run.
  5. Retain the receipt and finish prize requirements. Save the organizer’s result alongside the exact file hash. The official rules require selecting one final prediction for both prize rounds, reproducible code/documentation for finalists, and disclosure of generative-AI use in the narrative where applicable.
