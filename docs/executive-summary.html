Submission guide

How to make a submission into the contest

The competition portal accepts a single-band GeoTIFF (.tif) or a .zip containing exactly one GeoTIFF, with your predictions for all faults in the region (problem description, "Submission format"). Steps, in order:

  1. Get a cleared file. Only a file whose run card says verdict: promote and ok_to_submit: true may be uploaded. Today no such file exists — the candidate above is held. The steps below describe the process once a file is cleared by the separate selector step.
  2. Download the file from the button above and verify its SHA-256 against the run card (e.g. sha256sum gemsdoesass2-…-zeros.tif must equal 65e3a775…572661 for the current candidate).
  3. Check the format yourself in 20 seconds. The file must be one float32 band, EPSG:32611, 100 m pixels, shape 3730×3292, geotransform (100, 0, 243350, 0, -100, 4508550), all values inside the study area in [0,1], and NaN or masked zeros outside (spec). This project's read-only checker: python scripts/validate_tif.py --sample data/bridge/sample_submission.tif YOURFILE.tif.
  4. Open the submission form at drivendata.org/competitions/306 → Submit → New submission.
  5. Choose the file in the "File to submit" field (a single .tif, or a .zip containing a single GeoTIFF).
  6. Enter the note (optional but required by our protocol): the unique short comment from the run card, at most 140 characters, e.g. GEMSDOESASS2 sparse-blind-conduit 22163d B=2 sep3 | off-catalogue blind faults | cc522684 | research. Use the run card's name and note verbatim so submissions can be told apart later.
  7. Submit and record the receipt. Save the submission-page confirmation (file name, timestamp, score). Only that page can turn a number into ORGANIZER-CONFIRMED. Copy it into the run card.
  8. Weekly cap: the official rules allow three submissions per week per entity (rules §3.2). Promotion to a real slot is a separate selector decision; this project spends no slot without it.

If the portal says "Predicted values must be in range [0, 1]"

Diagnosed from official text only — the rejected bytes were never available, so this is not a confirmed cause. The published spec says values must be between 0 and 1 and that "data outside the bounds is null or nan" (spec), which allows NaN outside the study area. But a portal-side check that simply tests min >= 0 and max <= 1 without ignoring NaN can report this exact error for a file whose NaN pixels make the comparison false (IEEE: any comparison with NaN is false). Two conventions are known-good:

  • NaN outside, finite inside — byte-for-byte the organizer template's mask (data/bridge/sample_submission.tif, NaN on 7,111,787 cells outside the footprint). This is the -nan.tif twin.
  • Finite everywhere, 0 outside — no NaN at all; everything in [0,1]. This is the -zeros.tif twin and the only variant that passes this project's strict whole-array check.

If a NaN-style file is rejected with the range message, upload the zeros twin. If a zeros file were ever rejected with the same message, the rejected bytes and the portal response must be captured before any diagnosis (IR-09).

Format is necessary, not sufficient

Passing the local format check does not approve a submission: novelty (lane rules), scientific validation (HOLDOUT-DTI with 95% CI), leakage canaries and the separate selector step all apply first. Local validation is not a guarantee of portal acceptance, and a holdout score is not a leaderboard score.

The decisive gate

Why the candidate is held, and what would clear it

Against the pinned 13GEMSDOE lattice (a real leaderboard submission, 20261001_r13-lattice-s5), the sparse candidate has 22,106 of its 22,163 dots within 3 px (99.74%). The lane rule says: if more than 70% of your dots fall within 3 px of one registry raster's dots, log a duplicate and stop. By that text, the candidate is a duplicate of the lattice-family and must stop. The earlier "pass" came from a tool exemption for space-filling rasters; the literal rule has no such exemption.

Only 6,649 of the 5,167,373 footprint cells lie more than 3 px from the lattice, and every one of them is within 2.24 px of the study-area border. Checked against the corpus: the three existing "lattice-avoiding" files (3,165 / 505 / 6,430 dots) reach 0.0000 lattice overlap only with 100% of their dots on the border. Clearing 70% at 22,163 dots would require 6,649 dots — every far cell — on the border. No interior fault-targeting placement can do that, so the rule as written blocks geology, not duplication. Owner ruling needed, one of: (1) waive the lattice for space-filling probes and use the rank-correlation gate; (2) redefine "dots" for probability maps; (3) keep the literal rule and accept that only border-placed rasters pass; (4) keep submissions stopped.
