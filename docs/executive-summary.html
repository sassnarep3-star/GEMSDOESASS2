Decision needed from the owner

  1. Waive the lattice rule for footprint-wide rasters and use another test the protocol names, such as rank correlation above 0.90. This must be computed and ruled on first.
  2. Keep the literal rule. Then no footprint-wide candidate can be cleared. Only sparse placements (about 22,163 dots or fewer, with at least 30% in the 6,649 uncovered cells) would pass, and those carry no geological meaning. Not recommended.
  3. Define "dots" for probability maps (the official format) before the rule is applied to them.
  4. Stop submissions until one of the above is decided. This is the current status.

The owner's choice decides whether any future candidate is eligible. Until then, nothing in this repository is cleared for upload.

What the official metric and format require

The official metric is a distance-weighted Tversky index on probabilities in [0,1]. Outside the bounds the file may be null or NaN. The full formula, reference-solution details, and the leaderboard snapshot are in knowledge/03. The repository now implements the probabilistic form as dti_probabilistic (tests pass).

The reported "[0, 1]" error

The nine top files and the organizer sample contain only finite values in [0,1] inside the footprint, so none of the local copies reproduces the error. The spec allows NaN outside the footprint, and the organizer's sample uses it, so the spec does not make NaN the cause. Our own strict validator is stricter: it rejects NaN outside, and it rejects the organizer's sample for that reason (IR-S-11). The rejected bytes and the portal's response would settle the question; they were not supplied.

The decisive gate

Why the latest TIFFs are blocked

Against the pinned 13GEMSDOE lattice, HVFD has 37,617 of 37,654 dots within 3 pixels (99.9017%); XGHF has 37,636 of 37,654 (99.9522%). Both exceed the 70% limit. A comparison excluding the lattice cannot override the literal rule.

Only 6,649 footprint cells are farther than 3 pixels from that lattice. At 37,654 distinct dots, even an optimally placed set must overlap at least 31,005 times (82.34%). A smaller budget might avoid this particular mathematical bound, but still requires full uniqueness and holdout validation.

Format is necessary, not sufficient

The two latest research TIFFs pass the conservative local format policy against a hash-pinned owner mirror: one float32 band, matching geometry, no NaNs inside the footprint, all stored values finite in [0,1] and an external validity mask. How to submit a future approved file

These instructions apply only after all gates and a separate weekly-slot selector approve a new candidate. Nothing currently qualifies.

  1. Verify the run card. Check the surface and final registry scans, feature canaries, same-protocol holdout and 95% CI, saved-byte validation, and selector approval.
  2. Check the live account allowance. Sign in to DrivenData and read the current limit shown on its submission page.
  3. Download the approved file and verify its SHA-256. Use one single-band float32 GeoTIFF or a ZIP containing one TIFF. Match the organizer template's CRS, shape and geotransform; keep predictions in [0,1]. See the official format.
  4. Open New submission. Choose the file, enter the run card's unique note (at most 140 characters under this protocol), and submit. Save the organizer receipt with its exact file hash.
  5. Preserve reproducibility. Retain code, sources, licensing and required generative-AI disclosure under the official rules.

Local validation is not a guarantee of portal acceptance, and a holdout score is not a leaderboard score.
