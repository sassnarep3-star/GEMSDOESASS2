Root-Cause Fix: Why DrivenData Returned "Predicted values must be in range [0, 1]"

Earlier submissions across sibling repos triggered DrivenData's portal error "Predicted values must be in range [0, 1]" for three distinct byte-level reasons — all three are eliminated and regression-tested in src/gems_sass2/submission.py and tests/test_gems_sass2.py:

  1. Unmasked NaN or -9999.0 sentinel values: If a portal validator runs (arr >= 0.0).all() & (arr <= 1.0).all() on raw band arrays before applying the valid-footprint mask, any NaN or -9999 outside the footprint evaluates to False. Following drivendataorg/gems-prize-reference-solution Cell 19, our primary -zeros.tif sets nodata=None and writes exact 0.0 outside the footprint so all 12,279,160 pixels are strictly finite in [0.0, 1.0].
  2. float64 → float32 rounding / unclipped kriging overshoot: Continuous interpolation or unclipped sigmoid/tree blends can emit 1.0000001 or -1e-7. Our writer applies explicit np.clip(..., 0.0, 1.0).astype(np.float32) and re-reads the saved GeoTIFF from disk via rasterio to verify min == 0.0 and max == 1.0.
  3. Interior footprint holes: Raw external rasters (such as 1-m LiDAR with 75.37% coverage or sparse point probes) contain missing regions inside the 5,167,373-pixel footprint; xghf_features.py fills all channels via nearest-neighbor / Gaussian kernel regression prior to inference so zero NaNs can ever enter the valid footprint.
