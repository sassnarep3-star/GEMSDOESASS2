Reading the table: every reported top-nine file is one lineage. The GEMSDOE32 file is GEMSDOE25 with the 6,436 dots that sat within 2 px of the known catalogue removed (pixel-exact, receipt). Its gain over GEMSDOE25 is consistent with those dots having a new-fault hit rate below α·DTI ≈ 0.052. That is an inference from user-reported scores, not a measurement.

Why 0.2778 scored highest, and whether we can beat it

  1. Metric: DTI with α = 0.2 and β = 0.8. A false negative costs four times a false positive, so recall dominates.
  2. Marginal rule (derived and checked numerically, 20,000 trials, 0 violations): keep a dot only if its probability of hitting an unmapped fault exceeds α·DTI. At DTI ≈ 0.28 that threshold is about 5.6%.
  3. Consequence: the 0.2778 file gained only by dropping near-catalogue dots, which are the ones least likely to fall on a new fault. Beating it needs calibrated per-pixel posteriors and a dot or area set that keeps every pixel above the threshold. No posterior has been validated here, so we cannot claim a higher score.

Diagnosing "Predicted values must be in range [0, 1]"

We do not have the rejected bytes or the portal's response, so the cause is not confirmed. Measured facts: every nine-site file passes the whole-array [0, 1] guard. A NaN-outside file fails that naive guard, which is a plausible cause if a NaN file was uploaded. The zeros file has no NaN and carries a TIFF internal mask on the outside cells, so it passes both a naive guard and a mask-aware null check. The zeros file is the safer upload.
